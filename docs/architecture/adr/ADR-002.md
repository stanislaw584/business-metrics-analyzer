# ADR-002. Выбор СУБД: PostgreSQL

## Статус

Принято

## Контекст

Система хранит до 1 млн записей о продажах, пользователей, справочники метрик и журнал аудита. Дашборд строит агрегаты (суммы, количество чеков) по периодам, отделам и менеджерам, и пересчёт должен укладываться в 3 секунды (NFR-01). С системой одновременно работают несколько десятков пользователей, а импорт идёт параллельно с чтением. Данные должны храниться на серверах компании (CN-04), платные лицензии не закладываются (CN-02).

## Решение

Основная СУБД – PostgreSQL 16 в Docker-контейнере с постоянным томом `pgdata`. Доступ из приложения через SQLAlchemy 2, схема ведётся миграциями Alembic. Для ускорения агрегатов используются индексы по `(sale_date, department)` и материализованное представление с дневными итогами, которое обновляется после импорта.

## Альтернативы

1. SQLite – не требует сервера и удобна для учебного прототипа, но блокирует запись на уровне файла, плохо переносит одновременный импорт и чтение и не подходит для многопользовательской работы.
2. MySQL – зрелая и бесплатная, но слабее в аналитических запросах: нет материализованных представлений, оконные функции и типы данных беднее.
3. ClickHouse – очень быстрые аналитические агрегаты, но неудобна для транзакционных данных (пользователи, роли, справочники) и добавляет вторую СУБД, что избыточно при 1 млн строк.

## Последствия

- \+ надёжные транзакции, на которые опирается Unit of Work при пакетном импорте;
- \+ оконные функции и материализованные представления для расчёта KPI;
- \+ бесплатная лицензия и развёртывание в периметре компании;
- − нужен отдельный контейнер, резервное копирование тома и мониторинг;
- − для локальной разработки и тестов разработчикам нужен Docker (или SQLite через тот же интерфейс репозитория).
