# ADR-004. Кэширование KPI в Redis

## Статус

Принято

## Контекст

Дашборд открывают каждое утро несколько десятков пользователей, при смене периода KPI должны обновляться не дольше чем за 3 секунды (NFR-01, AC-01.2). Расчёт по году данных (до 1 млн строк) с группировкой по отделам занимает больше времени, чем допускает требование. Данные о продажах меняются только при импорте, обычно раз в день.

## Решение

Результаты расчёта KPI кэшируются в Redis 7 через компонент `RedisKpiCache`. Ключ строится из периода, отдела и набора метрик, например `kpi:2026-10:dept-1`, время жизни записи – 24 часа. После каждого импорта событие `SalesImported` (паттерн Observer) сбрасывает ключи затронутых периодов и запускает предрасчёт KPI за текущий и прошлый месяц.

## Альтернативы

1. Без кэша, только индексы и материализованные представления PostgreSQL – проще, но при росте данных и числа пользователей время отклика не гарантируется.
2. Кэш в памяти процесса (`functools.lru_cache`) – не нужен отдельный контейнер, но кэш теряется при перезапуске и не общий для нескольких экземпляров API.
3. Предрасчёт всех KPI в отдельную таблицу БД – быстро читается, но любая новая метрика или срез требует изменения схемы и пересчёта всей таблицы.

## Последствия

- \+ ответ дашборда из кэша за миллисекунды, требование ≤ 3 с выполняется с запасом;
- \+ снижается нагрузка на PostgreSQL в утренние часы;
- \+ Redis позже используется как брокер очереди задач для импорта (см. [ADR-005](ADR-005.md));
- − ещё один контейнер в развёртывании;
- − риск показать устаревшие данные, если сброс кэша не сработает, поэтому стоит TTL 24 часа и сброс по событию.
