# ADR-003. Способ аутентификации: JWT с ролевым доступом

## Статус

Принято

## Контекст

В системе пять ролей: коммерческий директор, руководитель отдела, менеджер по продажам, аналитик и администратор. Менеджер видит только свои показатели, руководитель отдела – свой отдел (US-04, AC-04.2). Все страницы закрыты авторизацией, пароли хранятся в виде хеша (NFR-02). REST API используется веб-интерфейсом, в будущем – мобильным клиентом (US-10).

## Решение

Аутентификация по JWT. После входа `AuthService` выдаёт access-токен со сроком жизни 30 минут и refresh-токен на 7 дней. В access-токене передаются идентификатор пользователя, роль и отдел. Каждый запрос проверяется зависимостью FastAPI, а фильтрация данных по роли выполняется в Service Layer. Пароли хранятся как хеши bcrypt, после 5 неудачных попыток вход блокируется на 15 минут (AC-04.3).

## Альтернативы

1. Серверные сессии с cookie – токен легко отозвать, но состояние хранится на сервере (в Redis или БД), а мобильному клиенту и нескольким экземплярам API работать с сессиями сложнее.
2. Внешний провайдер (OAuth 2.0 / OpenID Connect, например Keycloak или корпоративный AD) – единый вход и централизованное управление, но требует отдельной инфраструктуры и интеграции, что избыточно для MVP.
3. HTTP Basic Auth – проще всего, но пароль передаётся с каждым запросом и нет удобного способа передать роль.

## Последствия

- \+ API не хранит состояние сессий и легко масштабируется на несколько экземпляров;
- \+ один механизм для веб-интерфейса и будущего мобильного клиента;
- \+ роль и отдел в токене позволяют фильтровать данные без лишнего запроса к БД;
- − токен нельзя отозвать до окончания срока, поэтому срок access-токена короткий, а при блокировке пользователя отзываются refresh-токены;
- − секретный ключ подписи нужно хранить вне репозитория (переменные окружения, `.env` в `.gitignore`).
